# x402 with Circle Nanopayments on Arc testnet

Status: spike for issue #6, run on 2026-11-15.
The seller, the buyer, the 402 challenge and the signed paid retry all work against the live Circle Gateway testnet facilitator.
The paid retry was rejected with `insufficient_balance` because the buyer wallet has no testnet USDC yet: the Circle faucet needs a browser, and its API needs a Circle API key.
A successful paid request, the deposit and our own settlement on chain are therefore still open (see [Run it once funded](#run-it-once-funded)).

Every statement is tagged:

- **(ran)**: verified by running it on 2026-11-15.
- **(docs)**: verified in current primary docs or in the published SDK source.
- **(unverified)**: believed true, not yet checked.

## How it works

1. The buyer deposits USDC into Circle's GatewayWallet contract on Arc with one onchain transaction (docs).
2. The buyer requests the paid route and gets `402 Payment Required` with a base64 JSON `PAYMENT-REQUIRED` header (ran).
3. The buyer signs an EIP-3009 `TransferWithAuthorization` offchain, with the GatewayWallet as the EIP-712 verifying contract, and retries with a `Payment-Signature` header (ran).
4. The seller asks Circle Gateway to verify and settle; Gateway locks the buyer's balance and the seller serves the response with a `PAYMENT-RESPONSE` header (docs; the rejection path ran).
5. Gateway later settles many authorizations in one `submitBatch` transaction on the GatewayWallet (ran, observed on other users' transfers).

Neither party pays gas per request; only the deposit (and a later withdrawal) are onchain transactions (docs).

## Seller: Hono, not Express

`signals` uses Hono with `@x402/hono`, an `x402ResourceServer`, Circle's `BatchFacilitatorClient` and Circle's `GatewayEvmScheme` (`signals/src/app.ts`).
Circle's one-line `createGatewayMiddleware()` is written against Node `IncomingMessage`/`ServerResponse` plus an Express-style `next`, so it does not plug into Hono (docs, SDK source).
Circle documents the `x402ResourceServer` + `BatchFacilitatorClient` + `GatewayEvmScheme` combination as the way to add Nanopayments to any standard x402 server (docs: "How-to: Add nanopayments to an x402 seller").
`@x402/hono` is the Hono adapter for that same server, and the stock `GatewayClient` buyer pays it without changes (ran: 402 decoded, payload signed, paid retry reached Gateway).

Routes:

- `GET /health`: free.
- `GET /v1/resources`: free discovery document listing each paid route with price, amount in base units, asset, network, seller and an example response.
- `GET /v1/signal/hello`: paid, $0.001 (1000 base units).

To add a paid route (issue #20), write a `PaidRoute` (`signals/src/paid-route.ts`) and pass it to `createSignalsApp({ routes })`; the app registers the handler, the paywall entry and the discovery entry from that one object.
The seller address comes from `X402_SELLER_ADDRESS`, or is derived from `X402_SELLER_PRIVATE_KEY`; the server never uses the key for anything else.

`BatchFacilitatorClient` defaults to the mainnet Gateway API (`https://gateway-api.circle.com`), whose `/v1/x402/supported` does not list `eip155:5042002`; pass the testnet URL explicitly (ran).

## Buyer

`agent/src/x402/buyer.ts` wraps Circle's `GatewayClient`:

- `ensureDeposit({ minAvailable, depositAmount })`: deposits from the wallet when the Gateway available balance is low, then polls until Gateway credits it.
- `pay(url, { maxPrice })`: pays only if the seller's price is at most `maxPrice`, and returns `{ status, data, receipt }`.
- `transferFor(receipt)`: looks the payment up in Gateway's transfer history by nonce.

The price cap runs in the SDK's `onBeforePaymentCreation` hook, which fires before the authorization is signed (ran: test asserts `signTypedData` is never called and no `Payment-Signature` is sent).
Per-call state lives in `AsyncLocalStorage`, so overlapping calls on one client keep separate caps (ran, test).
Rejections are typed: `PriceAboveMaximumError` (refused before signing), `PaymentRejectedError` with Gateway's reason, `InsufficientWalletBalanceError` naming the address to fund (all ran against live Gateway or tests).

The receipt (`X402Receipt`) holds `amount` (base units), `amountUsdc`, `asset`, `payer`, `payee`, `network`, `nonce`, `settlementId`, `validBefore`, `paidAt` and `latencyMs`.
`settlementId` is the `transaction` field of `PAYMENT-RESPONSE`; for Gateway batching we expect a Gateway transfer reference rather than an onchain hash (unverified until a funded run).
The `nonce` is the reliable key: Gateway's transfers API can be searched by it and returns exactly that transfer (ran on another user's settled transfer).

## Setup, step by step

1. `npm install` at the repository root (ran).
2. `npm run x402:keygen` appends `X402_BUYER_PRIVATE_KEY` and `X402_SELLER_PRIVATE_KEY` to the root `.env` (mode 600) if they are missing, never overwrites, and prints only the addresses (ran).
   Set `ENV_FILE=/path/to/.env` to use another file; every script reads `ENV_FILE` first.
3. Fund the buyer address with testnet USDC at https://faucet.circle.com (Arc Testnet).
   USDC is also the gas token, so one faucet drip covers the deposit and its gas (docs).
   The faucet is a browser page; the programmatic faucet `POST https://api.circle.com/v1/faucet/drips` answers `401 Invalid credentials` without a Circle API key (ran).
   The 20 USDC per 2 hours allowance is from our earlier notes (unverified).
4. `npm run signals:start` starts the seller on port 4021 (ran).
5. `npm run x402:hello -- --wait-settlement` deposits 1 USDC if the Gateway balance is below the price, pays the hello route with a $0.001 cap, prints the receipt, and then follows the Gateway transfer until its batch lands onchain (code ran up to the deposit check; the funded path is unverified).
6. `npm run x402:status` prints wallet and Gateway balances for buyer and seller and the buyer's recent Gateway transfers (ran).

## Settlement and what shows up onchain

- Gateway transfer statuses go `received`, then `batched`, `confirmed`, `completed`, or `failed` (docs).
  Treat `confirmed` as paid for accounting and wait for `completed` before anything that depends on the funds onchain (docs).
- Gateway's transfer history is public and needs no API key: `GET https://gateway-api-testnet.circle.com/v1/x402/transfers?from=<payer>&network=eip155:5042002` (also `to`, `nonce`, `status`, `startDate`, `endDate`, `pageSize`, `pageAfter`; pagination in a `Link` header) (ran).
  Each item has `id`, `status`, `fromAddress`, `toAddress`, `amount` (base units), `nonce`, `txHash` (null until settled), `createdAt` and `updatedAt` (ran).
- Batches are frequent: four transfers from another testnet user created between 19:55:27 and 20:00:39 UTC all completed at 20:01:07 in one transaction, so a payment took between 30 seconds and 6 minutes to land onchain (ran).
  That batch is [`0x65303d55...0fc9638`](https://explorer.testnet.arc.io/tx/0x65303d55a2660392d1b01f52285d8bab24dd46ded3c27773657e5e33a0fc9638).
- A batch is one `submitBatch(bytes calldataBytes, bytes signature)` call to the GatewayWallet that emits a single `BatchProcessed(bytes32 indexed batchId, address indexed signer, address indexed tokenAddress)` event and no ERC-20 `Transfer` logs (ran, decoded by the explorer).
  Individual payments are therefore not visible as onchain events; the explorer shows the batch, and the per-payment record is Gateway's transfer history.
- Deposits are ordinary onchain transactions on the GatewayWallet and emit `Deposited(token, depositor, sender, value)` (docs).
- Balances: `POST https://gateway-api-testnet.circle.com/v1/balances` with `{"token":"USDC","sources":[{"domain":26,"depositor":"0x..."}]}` returns `balance` and `pendingBatch` (ran).
- Gateway waits about one Arc block, about 0.5 seconds, before crediting a deposit (docs); our measured credit time is unverified.
- Sellers withdraw from their Gateway balance; same-chain withdrawal is instant (docs).

## Limits and gotchas

- Minimum payment is $0.000001 (docs); our hello route charges $0.001.
- Authorizations must stay valid at least 7 days: Gateway publishes `minValiditySeconds: 604800` and the SDK signs for 604,900 s regardless of the seller's `maxTimeoutSeconds` (ran).
  Circle's own `arc-nanopayments` sample still advertises 345,600 s (4 days); the SDK clamps it, a hand-rolled buyer would not.
- Nanopayments accept EOA signatures only; ERC-1271 smart accounts are not supported (docs).
- Arc enforces a 20 gwei `maxFeePerGas` floor; below it a transaction may stay pending forever or fail (docs); `eth_gasPrice` returned exactly 20 gwei (ran).
  viem and the SDK price deposits from the node, so this only bites hand-built transactions.
- USDC is 18 decimals as the native gas balance and 6 decimals through the ERC-20 interface (docs); every amount in x402 and Gateway is in 6-decimal base units (ran).
- The EIP-712 domain is `name "GatewayWalletBatched"`, `version "1"` (or `"2"` with a salt), `chainId 5042002`, `verifyingContract` the GatewayWallet (docs, SDK source).
- With `@x402/hono`, the route handler runs after verify and before settle; if settle then fails, the client gets a 402 and the handler's output is discarded (SDK source, and the live rejection above).
  Paid handlers must be safe to run without being paid: compute, no side effects.
- `GatewayClient.pay` parses every response body as JSON, so paid routes must return JSON (SDK source).
- Browsers sending `Accept: text/html` get the x402 paywall page, which needs the optional `@x402/paywall` package we do not install (SDK source, unverified in practice).
- Circle's other product, the Facilitator Service at `https://api.circle.com/v1/facilitator/x402`, settles each payment onchain from the buyer's own wallet with no deposit, supports `exact` and `upto` on `eip155:5042002`, and has a keyless trial (ran: `/supported`; docs).
  It is the better fit for larger, less frequent payments; Nanopayments fit our sub-cent per-request signal.
